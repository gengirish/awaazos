Whose data is it?

Ravi runs a chai stall. Suresh runs a dosa cart. They both use the same AwaazOS website, the same database, the same code. So how does the system guarantee Ravi will never see one rupee of Suresh’s sales? This is the most important security idea in the codebase.

The apartment building

Picture a 50-storey apartment building. There’s one big front door for the whole building — you can’t even step inside without buzzing in. Past that, each apartment has its own keycard reader.

Even if you live on floor 5 and have a working keycard, that card won’t open the door on floor 7. The reader is configured to only accept the keycard for that specific apartment. You don’t need to be a security guard to enforce this — the reader does it automatically.

🏢
Two layers, on purpose

The front door = authentication. The keycard reader on each floor = authorization. Mix them up and you get either a building you can’t enter, or a building anyone can wander through.

The data model

To make tenancy work, the database needs to know “this menu item belongs to which shop?” The answer is the vendorId column on (almost) every table.

👤
User

A person with an email and password. Can be staff at one or many vendors.

🏪
Vendor

The tenant. The chai stall, dosa cart, kirana shop. Vendor.id is the apartment number.

🔗
StaffMember

The keycard. Joins one User to one Vendor with a role (OWNER, MANAGER, or CASHIER).

🍛
MenuItem, Transaction, Receipt…

Every other row carries a vendorId. That column is the difference between Ravi’s data and Suresh’s.

🔑
Two-layer roles

UserRole (USER, ADMIN, SUPER_ADMIN) is the platform role — AwaazOS internal staff.
StaffRole (CASHIER, MANAGER, OWNER) is the per-vendor role. A user can be OWNER at one stall and CASHIER at another. Both roles exist for different reasons.

The function every protected route calls

Almost every API route in this codebase starts with one line: const ctx = await requireVendorRole("CASHIER", undefined, req). That helper does all the work. Here’s the heart of it.

CODE · lib/rbac.ts 
const session = await auth();
if (!session?.user?.id) {
  throw new AuthError(401, "Unauthorized");
}

const memberships = await prisma.staffMember.findMany({
  where: { userId: user.id, isActive: true },
  include: { vendor: true },
  orderBy: { createdAt: "asc" },
});

if (!memberships.length) {
  throw new AuthError(403, "No vendor membership.");
}

const target = vendorIdOrSlug ?? querySlug ?? cookieSlug;
let staff = target
  ? memberships.find((m) => m.vendor.slug === target || m.vendorId === target)
  : memberships[0];

if (!staffRoleAtLeast(staff.role, minRole)) {
  throw new AuthError(403, "Requires staff role MANAGER or higher.");
}
PLAIN ENGLISH

Read the signed-in user from the session cookie.

No session? Bounce them with a 401 Unauthorized.

Look up every active vendor this user is a staff member of (a person can work at multiple stalls).

No memberships at all? Bounce with 403 Forbidden.

Pick the active vendor: an explicit argument wins, then a URL ?vendor= query parameter, then a cookie, then the oldest membership.

Find the matching StaffMember record for that vendor.

Check the user’s role at this vendor is at least the minimum required (e.g., MANAGER).

Bounce with 403 if they’re too junior. Otherwise return the user, vendor, and staff record — the route handler picks up from here.

The bug that costs companies millions

One of these lines is a tenant-leak waiting to happen. Tap the line you think is dangerous.

This API route lets a vendor edit a menu item by ID. Find the line that lets one vendor edit any other vendor’s menu items.

1 const ctx = await requireVendorRole("MANAGER");
2 const { id } = params;
3 const body = menuItemSchema.parse(await req.json());
4 await prisma.menuItem.update({ where: { id }, data: body });
5 return NextResponse.json({ ok: true });
🚨
IDOR — the boring vulnerability that ships every year

The fix is a single property: where: { id, vendorId: ctx.vendor.id }. With that compound where, even if Ravi knows Suresh’s menu-item ID, the update silently affects zero rows — the database refuses because the combo doesn’t exist. AwaazOS returns 404 (not 403) on these so attackers can’t even confirm the ID is real.

The credentials check, in one block

For sign-in, AwaazOS uses Auth.js with a Credentials provider — meaning email + password (no Google, no OTP yet). Here’s the heart of the password check.

CODE · lib/auth.ts 
Credentials({
  credentials: { email: {...}, password: {...} },
  async authorize(credentials) {
    const { email, password } = await signInSchema.parseAsync(credentials);
    const normalizedEmail = email.trim().toLowerCase();
    const user = await prisma.user.findUnique({
      where: { email: normalizedEmail },
      select: { id: true, passwordHash: true, ... },
    });
    if (!user?.passwordHash) return null;
    if (!(await verifyPassword(password, user.passwordHash))) return null;
    return { id: user.id, email: user.email, ... };
  },
})
PLAIN ENGLISH

We’re telling Auth.js to use the email-and-password sign-in method.

When someone tries to sign in, validate the input against a Zod schema — bad input bounces here.

Trim the email and lowercase it so “ravi@chai.com” and “Ravi@Chai.COM” both find the same user.

Look up the user by email. Note the select — we ONLY pull the password hash and a few safe fields, not everything.

If we don’t find a user, return null — Auth.js treats this as “sign-in failed.”

Compare the entered password with the stored hash using bcrypt. Bcrypt never decrypts the stored hash — it re-hashes the entered password and checks if it matches.

If everything checks out, return the user’s safe-to-share fields. Auth.js puts these in the JWT session cookie.
