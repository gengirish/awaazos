01

Bol. Bill. Becho.

A chai-wala in Hyderabad taps an orange button and says “do samosa aur ek chai.” Less than two seconds later, the customer’s phone is showing a UPI QR code. This module follows every single thing that happens in between.

What this thing actually does

AwaazOS is a point-of-sale system for India’s 25 million micro-merchants — chai stalls, dosa carts, paan shops, kirana stores. The kind of place where the owner takes orders verbally in Hindi or Telugu, and writing them down by hand loses about 15–20% of revenue every month.

The pitch is one line: tap a button, speak the order in any Indian language, get a bill and a UPI QR code. No typing. No menus to navigate. No English required.

🎙️
The whole product, in one sentence

If a chai-wala can’t take their first 100 voice orders without thinking, every other feature is a distraction. The codebase is organised around protecting that one experience.

A backstage tour

Imagine you’ve just watched a 90-minute play. The acting was great, but you have no idea what the stagehands were doing behind the curtain — the lighting cues, the prop swaps, the quick costume changes that made it all feel effortless.

This module is that backstage tour for one specific scene: the moment a vendor speaks an order. Everything else in the course unpacks one of these stagehands in detail.

The mic button — small code, lots of states

The button itself is one of the most-touched pieces of the whole product. It has six visual states (idle, listening, transcribing, parsing, success, error) and every one is announced to screen readers. Here’s the core of it.

CODE · components/pos/VoiceOrderButton.tsx 
<button
  type="button"
  onClick={() => {
    if (state === "listening") stopListening();
    else startListening();
  }}
  aria-label={label}
  aria-pressed={state === "listening"}
  className={cn(
    "relative flex h-20 w-20 shrink-0 ...",
    state === "idle" && "bg-primary ...",
    state === "listening" &&
      "bg-destructive ... motion-safe:animate-pulse",
  )}
>
PLAIN ENGLISH

Make a clickable button on the page.

When tapped, ask: am I already listening? If yes, stop. If no, start.

Tell screen readers what the button currently means right now (idle? listening?). The label changes with the state.

Tell screen readers whether the button is “pressed” (which is what listening feels like).

Pick the visual look based on the state. Idle = solid orange. Listening = red with a pulse animation, but only if the user hasn’t turned animations off.

The pulse only animates for users who haven’t enabled the “reduce motion” accessibility setting on their phone.

♿
Why every state has a label

About 12% of Indian phone users have a vision impairment of some kind. Screen readers rely on aria-label and aria-pressed to narrate what just happened — without them, a blind chai-wala can’t use the product. Add accessibility on day one.

A budget for every step

Voice products live or die on latency. If a vendor has to wait three seconds after speaking, they’ll go back to writing on paper. This codebase has a published time budget for every leg of the journey.

🎤

Browser → Server

~80 ms median. Just the network hop from the vendor’s phone to Vercel.

🗣️

Speech → Text

~1.2 s for Indic languages via Sarvam. Free & instant for English/Hindi via the browser.

🧠

Text → Items

~350 ms for Claude Haiku to match the menu. Roughly the time it takes to blink three times.

💾

Save the sale

~90 ms to atomically write all five rows to Postgres.

Add it up: about 1.8 seconds from speech to QR code on a typical day. P95 (the slowest 5% of requests) tops out around 3.7 seconds.

The Cast: three providers, one alias

When you visit awaazos.vercel.app, it feels like one app. Behind the curtain, three different cloud companies and four external APIs are doing different jobs. Here’s who does what — and, just as importantly, why none of them does everything.

The right tool for the job

Picture a wood-working workshop. You have a circular saw for straight cuts, a router for edge profiles, a drill press for clean perpendicular holes. You wouldn’t ask the circular saw to also drill holes — the result would be terrible at both jobs. You pick the specialist tool for each task.

AwaazOS is the same. Each provider in the stack is the best in the world at one specific thing. Putting everything on one provider would be slower, more expensive, or less reliable.

🛠️
Engineers call this “separation of concerns”

One component, one job. The benefit isn’t academic — it’s that when something breaks, you know exactly which specialist to call.

Why the workers live somewhere else

This is the most-asked question about the architecture. Here’s the simple version: a Vercel serverless function is fast for short jobs, but it’s a terrible fit for the kind of work that needs to wait around — like watching a queue for new WhatsApp jobs.

⚡

Serverless (Vercel)

Wakes up, runs for <10 seconds, sleeps. Perfect for “take this voice clip and parse it.” Bad at “wait around forever for jobs.”

⚙️

Long-running (Fly.io)

A small Linux box that’s always on. Holds a TCP connection to Redis. Picks up jobs the second they appear. Perfect for queue workers.

🗄️

Database (Neon)

Stores everything. Both Vercel and Fly read/write to the same Neon database — that’s how the two halves of the system stay in sync.

💡
The two-Redis trick

You’ll see two Redis instances in the diagram. They’re different on purpose. Upstash REST talks over HTTP and is used by Vercel for rate-limiting. Regular TCP Redis is used by BullMQ on Fly because BullMQ needs to keep a connection open. You can’t use the wrong one in the wrong place.

The middleware in five lines

Every single request that hits AwaazOS — whether it’s a vendor visiting /menu or an API call to /api/transactions — passes through this tiny file first. It runs on Vercel’s edge in roughly 10 milliseconds.

CODE · middleware.ts 
import NextAuth from "next-auth";
import { authConfig } from "@/lib/auth.config";

export const { auth: middleware } = NextAuth(authConfig);

export const config = {
  matcher: [
    "/((?!_next/static|_next/image|favicon.ico|api/webhooks|api/health|api/ready).*)",
  ],
};
PLAIN ENGLISH

Bring in the Auth.js library and our shared auth settings.

Hand off the request to Auth.js. It checks the cookie for a valid session.

Tell Vercel which URLs this middleware should run on.

The matcher is a regex that says: “run on every URL except static files, webhook callbacks (those verify themselves), and health-check probes (uptime monitors must reach them anonymously).”

⚠️
Don’t accidentally protect a webhook

If /api/webhooks/razorpay were behind auth, Razorpay’s servers (which don’t have a vendor login) couldn’t reach it — and subscriptions would silently break. Excluding webhooks from the matcher is a small line with big consequences.

03

Whose data is it?

Ravi runs a chai stall. Suresh runs a dosa cart. They both use the same AwaazOS website, the same database, the same code. So how does the system guarantee Ravi will never see one rupee of Suresh’s sales? This is the most important security idea in the codebase.

The apartment building

Picture a 50-storey apartment building. There’s one big front door for the whole building — you can’t even step inside without buzzing in. Past that, each apartment has its own keycard reader.

Even if you live on floor 5 and have a working keycard, that card won’t open the door on floor 7. The reader is configured to only accept the keycard for that specific apartment. You don’t need to be a security guard to enforce this — the reader does it automatically.

🏢
Two layers, on purpose

The front door = authentication. The keycard reader on each floor = authorization. Mix them up and you get either a building you can’t enter, or a building anyone can wander through.

The data model

To make tenancy work, the database needs to know “this menu item belongs to which shop?” The answer is the vendorId column on (almost) every table.

👤
User

A person with an email and password. Can be staff at one or many vendors.

🏪
Vendor

The tenant. The chai stall, dosa cart, kirana shop. Vendor.id is the apartment number.

🔗
StaffMember

The keycard. Joins one User to one Vendor with a role (OWNER, MANAGER, or CASHIER).

🍛
MenuItem, Transaction, Receipt…

Every other row carries a vendorId. That column is the difference between Ravi’s data and Suresh’s.

🔑
Two-layer roles

UserRole (USER, ADMIN, SUPER_ADMIN) is the platform role — AwaazOS internal staff.
StaffRole (CASHIER, MANAGER, OWNER) is the per-vendor role. A user can be OWNER at one stall and CASHIER at another. Both roles exist for different reasons.

The function every protected route calls

Almost every API route in this codebase starts with one line: const ctx = await requireVendorRole("CASHIER", undefined, req). That helper does all the work. Here’s the heart of it.

CODE · lib/rbac.ts 
const session = await auth();
if (!session?.user?.id) {
  throw new AuthError(401, "Unauthorized");
}

const memberships = await prisma.staffMember.findMany({
  where: { userId: user.id, isActive: true },
  include: { vendor: true },
  orderBy: { createdAt: "asc" },
});

if (!memberships.length) {
  throw new AuthError(403, "No vendor membership.");
}

const target = vendorIdOrSlug ?? querySlug ?? cookieSlug;
let staff = target
  ? memberships.find((m) => m.vendor.slug === target || m.vendorId === target)
  : memberships[0];

if (!staffRoleAtLeast(staff.role, minRole)) {
  throw new AuthError(403, "Requires staff role MANAGER or higher.");
}
PLAIN ENGLISH

Read the signed-in user from the session cookie.

No session? Bounce them with a 401 Unauthorized.

Look up every active vendor this user is a staff member of (a person can work at multiple stalls).

No memberships at all? Bounce with 403 Forbidden.

Pick the active vendor: an explicit argument wins, then a URL ?vendor= query parameter, then a cookie, then the oldest membership.

Find the matching StaffMember record for that vendor.

Check the user’s role at this vendor is at least the minimum required (e.g., MANAGER).

Bounce with 403 if they’re too junior. Otherwise return the user, vendor, and staff record — the route handler picks up from here.

The bug that costs companies millions

One of these lines is a tenant-leak waiting to happen. Tap the line you think is dangerous.

This API route lets a vendor edit a menu item by ID. Find the line that lets one vendor edit any other vendor’s menu items.

1 const ctx = await requireVendorRole("MANAGER");
2 const { id } = params;
3 const body = menuItemSchema.parse(await req.json());
4 await prisma.menuItem.update({ where: { id }, data: body });
5 return NextResponse.json({ ok: true });
🚨
IDOR — the boring vulnerability that ships every year

The fix is a single property: where: { id, vendorId: ctx.vendor.id }. With that compound where, even if Ravi knows Suresh’s menu-item ID, the update silently affects zero rows — the database refuses because the combo doesn’t exist. AwaazOS returns 404 (not 403) on these so attackers can’t even confirm the ID is real.

The credentials check, in one block

For sign-in, AwaazOS uses Auth.js with a Credentials provider — meaning email + password (no Google, no OTP yet). Here’s the heart of the password check.

CODE · lib/auth.ts 
Credentials({
  credentials: { email: {...}, password: {...} },
  async authorize(credentials) {
    const { email, password } = await signInSchema.parseAsync(credentials);
    const normalizedEmail = email.trim().toLowerCase();
    const user = await prisma.user.findUnique({
      where: { email: normalizedEmail },
      select: { id: true, passwordHash: true, ... },
    });
    if (!user?.passwordHash) return null;
    if (!(await verifyPassword(password, user.passwordHash))) return null;
    return { id: user.id, email: user.email, ... };
  },
})
PLAIN ENGLISH

We’re telling Auth.js to use the email-and-password sign-in method.

When someone tries to sign in, validate the input against a Zod schema — bad input bounces here.

Trim the email and lowercase it so “ravi@chai.com” and “Ravi@Chai.COM” both find the same user.

Look up the user by email. Note the select — we ONLY pull the password hash and a few safe fields, not everything.

If we don’t find a user, return null — Auth.js treats this as “sign-in failed.”

Compare the entered password with the stored hash using bcrypt. Bcrypt never decrypts the stored hash — it re-hashes the entered password and checks if it matches.

If everything checks out, return the user’s safe-to-share fields. Auth.js puts these in the JWT session cookie.

04

Speech becomes structure

When the vendor says “sat samosa, do chai, ek vada pav, pyaaz wala”, the computer first hears literal noise. By the time the cart fills, that noise is a structured list: [{ id, name, qty, price }, …]. This module follows the four steps that bridge those two worlds.

A translator with a sticky-note menu

Imagine a market translator standing next to a vendor. They don’t speak the customer’s language perfectly — they need a cheat sheet. So the vendor sticks a copy of the menu next to them, with each item highlighted.

When a customer says “two of those crispy onion ones,” the translator glances at the sheet, points at aloo bhujia, and tells the vendor “they want 2× aloo bhujia.”

The cheat sheet is the cached menu. The translator is Claude. The pointing is tool-use. The whole module is making this metaphor literal.

📌
Why every step in this pipeline costs money

The voice path is the per-order unit cost of the product. AwaazOS charges only ₹299/month, so the engineering choices here aren’t cosmetic — they’re what makes the pricing possible.

Step 1: pick the right speech-to-text engine

Two paths, decided by language. English and Hindi go through the browser’s built-in Web Speech API. Telugu, Kannada, and Tamil go to Sarvam.

📱

Web Speech (en-IN, hi-IN)

On-device. Free. No audio ever leaves the phone. The browser hands us back a text string in ~600 ms.

🌐

Sarvam Saaras v2 (te, kn, ta)

Server round-trip. The browser records 5–12 seconds of audio, ships it to /api/ai/transcribe, which forwards it to Sarvam. Costs roughly 1.2 seconds and a paisa per call.

CODE · hooks/useVoiceOrder.ts 
const SARVAM_LANGS = new Set(["te-IN", "kn-IN", "ta-IN"]);
const WEBSPEECH_LANGS = new Set(["en-IN", "hi-IN"]);

if (WEBSPEECH_LANGS.has(voiceLang)) {
  const Ctor = window.SpeechRecognition ?? window.webkitSpeechRecognition;
  if (!Ctor) { setState("error"); return; }
  const recognition = new Ctor();
  recognition.lang = voiceLang;
  recognition.start();
}

if (SARVAM_LANGS.has(voiceLang)) {
  const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
  const mr = new MediaRecorder(stream, { mimeType });
  mr.start();
  // 12-second hard timeout — even if vendor forgets to stop
  setTimeout(() => mr.stop(), 12_000);
}
PLAIN ENGLISH

Define two sets of languages — one handled in-browser, one handled by Sarvam.

For English/Hindi: ask the browser if it has a built-in speech recogniser. (Some don’t.)

If yes, kick it off in this language. The text comes back via callbacks.

For Indic languages: ask the OS for microphone access. The browser pops the “allow microphone?” prompt.

Start recording into a Blob (a chunk of audio in memory).

Set a hard 12-second cap so we don’t end up uploading a 10-minute clip if the vendor forgets to tap stop.

Step 2 & 3: cache the menu, force a tool call

Once we have the transcript, the menu plus transcript go to Claude. Two engineering choices make this cheap and reliable:

A
Cache the menu

For a 30-item menu, the JSON is ~2KB. Marking it cache_control: ephemeral tells Anthropic “this part doesn’t change between calls — reuse it.” The cache lives 5 minutes. During the lunch rush, every request after the first one pays ~75% less for that block.

B
Force a tool call

Instead of asking Claude for free-form JSON (which sometimes hallucinates trailing commas), we declare a add_items “tool” with a strict schema. Claude is forced to fill in that exact shape, so the answer is structured by construction.

CODE · lib/anthropic.ts 
const message = await modelClient.messages.create({
  model: modelName,
  max_tokens: 512,
  temperature: 0.1,
  system: ORDER_PARSE_SYSTEM,
  tools: [ADD_ITEMS_TOOL],
  tool_choice: { type: "tool", name: "add_items", disable_parallel_tool_use: true },
  messages: [
    {
      role: "user",
      content: [
        {
          type: "text",
          text: `Authoritative menu (JSON):\n${menuJson}`,
          cache_control: { type: "ephemeral" },
        },
        {
          type: "text",
          text: `Customer transcript (${lang}):\n${transcript}`,
        },
      ],
    },
  ],
});
PLAIN ENGLISH

Send a message to Claude. The model name is passed in — same code path for Haiku and Sonnet.

Cap the answer at 512 tokens. Order parsing answers are tiny.

Set temperature to 0.1 — we want consistent, boring, deterministic outputs.

Give Claude one tool it’s allowed to use: add_items. The schema lives in a separate constant.

Force Claude to call this exact tool, exactly once. No free-form text. No parallel calls.

First content block: the vendor’s menu as JSON. The magic line is cache_control: ephemeral.

That line tells Anthropic “remember this block” for the next 5 minutes. Subsequent requests during a busy lunch rush pay ~75% less for the same menu.

Second content block: the transcript itself. This part changes every call, so it’s NOT cached.

Step 4: when does the senior translator get called?

Haiku covers ~85% of orders. The other 15% — long, code-mixed, ambiguous — get escalated to Sonnet. The decision happens in one small function.

CODE · app/api/ai/parse-order/route.ts 
function shouldEscalate(
  result: Awaited<ReturnType<typeof parseOrderWithClaude>>,
  transcript: string,
): boolean {
  const words = wordCount(transcript);
  if (result.items.length === 0 && words > 3) return true;
  if (result.confidence === "low" && result.unmatched.length > 0) return true;
  return false;
}
PLAIN ENGLISH

A function that returns “true” if we should re-run the parse with the smarter (and pricier) model.

It looks at Haiku’s answer and the original transcript.

First trigger: Haiku found nothing, but the customer said more than 3 words. They probably ordered something — let Sonnet take another look.

Second trigger: Haiku flagged low confidence AND there are phrases it couldn’t map. Sonnet’s extra reasoning is worth the cost here.

Otherwise, trust Haiku. Sonnet stays asleep.

💡
A pattern with a name

This is called a cascade or two-tier model routing. Cheap-and-fast for the 85% case, smart-and-slow for the 15% edge cases. You can apply this to any AI feature: try the small model first, escalate only when needed. Easy to ask AI for: “add a confidence-based escalation from Haiku to Sonnet for this endpoint.”

Indic numerals — the prompt’s secret sauce

Vendors don’t say “two” — they say do, rendu, eradu, onnu. The model needs to know these mean numbers. So the system prompt teaches it.

CODE · lib/anthropic.ts (system prompt excerpt) 
Normalize Indic numerals:
- hi: ek=1, do=2, teen=3, char=4, paanch=5
- te: okati=1, rendu=2, moodu=3, naalugu=4, aidu=5
- kn: ondu=1, eradu=2, mooru=3, naalku=4, aidu=5
- ta: onnu=1, rendu=2, moonu=3, naangu=4, anju=5

Put any phrase you could NOT confidently map into unmatched.
confidence = low if unmatched.length > 0 OR the transcript is ambiguous.
PLAIN ENGLISH

A small, hand-crafted lookup table embedded in the system prompt.

Each line is one language — spoken numerals 1 through 5 in Hindi, Telugu, Kannada, and Tamil.

The model uses these as anchor points. (LLMs are good at extrapolating beyond explicit examples.)

Crucial rule: if any phrase doesn’t map to a menu item, list it in unmatched rather than guessing wrong.

If anything ended up in unmatched, the model must mark confidence as “low” — which (per the previous screen) triggers escalation to Sonnet.

Quick check

Why is the transcript NOT included in the cached block, even though it’s sent in the same Anthropic call as the cached menu?

A note on what doesn’t go to Claude

🔒
Customer phone numbers never reach the LLM

Only the transcript and menu JSON are sent to Anthropic. Customer phone, name, and UPI reference are scrubbed at the boundary — they exist in Postgres for re-sending receipts, but they never appear in a prompt or a log line. This is a rule baked into the project’s Cursor rules — meaning the AI coding assistant itself enforces it on every PR.

05

Money in paise — the atomic transaction

When the vendor taps Mark as Paid, five things must happen to the database. They have to either all succeed together or all fail together — never four out of five. This module is about the two disciplines that make that possible: integer paise math, and a five-step database transaction.

Synchronised swimmers

Picture a synchronised swimming team. On the count of three, all five swimmers dive together. They’re trained for one rule: if even one swimmer hesitates, none of them dive. They re-set, count again, dive together. The judges either see five splashes or zero. Never four.

Database transactions work exactly like this. AwaazOS’s “Mark as Paid” bundles five separate writes into one transaction:

1
Get the next bill number

Atomically increment today’s counter for this vendor. Becomes AWZ-20260430-0001.

2
Insert the Transaction row

Subtotal, tax, total, payment method, payment status — all in paise.

3
Insert each OrderItem

One row per line in the cart, with the price snapshotted at sale time.

4
Bump the DailySummary

Add this sale to today’s rollup so the analytics dashboard updates immediately.

5
Create the Receipt row

Marker that this transaction’s receipt has not yet been sent on WhatsApp.

If any one of these fails, all five roll back — the database returns to exactly the state it was in before the swimmer climbed onto the platform. No half-recorded sales. No bill numbers wasted. Ever.

Why paise, not rupees

Before we touch the transaction, we have to talk about the unit of money. AwaazOS stores every monetary amount as an integer number of paise. ₹20 is the integer 2000. ₹99.50 is 9950. Never decimals.

💸
Why floats are forbidden for money

Computers store decimal numbers like 0.1 and 0.2 approximately. Try this in any browser console: 0.1 + 0.2 === 0.3 evaluates to false. Add a tiny rounding error to a million sales and you’re off by hundreds of rupees, with no way to find which sale caused it. Integer paise dodges the entire problem.

CODE · lib/currency.ts 
export function rupeesToPaise(rupees: number): number {
  if (!Number.isFinite(rupees)) {
    throw new Error("Invalid rupee amount");
  }
  const scaled = rupees * 100;
  const rounded = Math.round(scaled);
  if (Math.abs(scaled - rounded) > 1e-9) {
    throw new Error("Rupee amount must have at most 2 decimal places");
  }
  return rounded;
}

export function formatINR(paise: number): string {
  if (!Number.isInteger(paise)) {
    throw new Error("paise must be an integer");
  }
  const rupees = paiseToRupees(paise);
  return new Intl.NumberFormat("en-IN", {
    style: "currency",
    currency: "INR",
    minimumFractionDigits: 2,
    maximumFractionDigits: 2,
  }).format(rupees);
}
PLAIN ENGLISH

Convert rupees (a friendly number like 20.5) into paise (the integer 2050).

Reject anything that isn’t a finite number — NaN, Infinity, etc.

Multiply by 100 to scale into paise.

Round to the nearest integer (in case the multiplication produced a tiny float artefact).

If the difference between the multiplication result and the rounded integer is bigger than a tiny epsilon, the user passed something like ₹20.005 — reject it explicitly rather than silently rounding.

Format paise back into a display string. Used everywhere on the screen.

Use the browser’s built-in en-IN formatter so we get correct Indian grouping (₹1,23,456 with the lakh comma in the right place) for free.

The five swimmers, in code

Here’s the heart of POST /api/transactions — the five writes wrapped in a single prisma.$transaction call.

CODE · app/api/transactions/route.ts 
const { transaction, receipt } = await prisma.$transaction(async (tx) => {
  const seq = await tx.billSequence.upsert({
    where: { vendorId_date: { vendorId: vendor.id, date: today } },
    create: { vendorId: vendor.id, date: today, lastSeq: 1 },
    update: { lastSeq: { increment: 1 } },
  });

  const ymd = formatBillDateYYYYMMDD(today);
  const billNumber = `AWZ-${ymd}-${String(seq.lastSeq).padStart(4, "0")}`;

  const transactionRow = await tx.transaction.create({
    data: {
      vendorId: vendor.id, billNumber,
      subtotalPaise: body.subtotalPaise, taxPaise: body.taxPaise, totalPaise: body.totalPaise,
      orderItems: { create: body.items.map((i) => ({
        menuItemId: i.menuItemId, name: i.name,
        priceInPaise: i.priceInPaise, qty: i.qty,
        totalPaise: i.priceInPaise * i.qty,
      })) },
    },
  });

  await tx.dailySummary.upsert({ /* increment all aggregates */ });

  const receiptRow = await tx.receipt.create({
    data: { transactionId: transactionRow.id, vendorId: vendor.id, receiptNumber: billNumber, whatsappSent: false },
  });

  return { transaction: transactionRow, receipt: receiptRow };
});
PLAIN ENGLISH

Open a database transaction. Everything inside the curly braces will commit together — or roll back together if anything throws.

Step 1 — Upsert the bill counter for (this vendor, today). If it doesn’t exist, create it at 1. If it does, add 1 atomically.

Format today’s date in IST as YYYYMMDD. Build the bill number string — e.g., AWZ-20260430-0001.

Step 2 — insert the Transaction row with all the paise totals.

Step 3 — nested inside, insert one OrderItem per cart line. Note name and priceInPaise are copied here, not joined — the bill is a snapshot, not a live link to the menu.

Step 4 — bump today’s rollup row so analytics see the sale immediately.

Step 5 — create the Receipt row, with a flag saying WhatsApp hasn’t been sent yet (a worker will flip that later).

If we got here, all five swimmers dove together. The transaction commits. We return the rows for the response.

Engineers call this property “atomicity”

It’s the “A” in ACID. The whole reason real businesses store money in databases like Postgres rather than in spreadsheets or in-memory caches: the transaction either commits in full or doesn’t happen at all. Cosmic rays could flip a bit, the server could die mid-write — either way, the database never ends up in a half-state.

The one allowed toFixed

The rule of the codebase: toFixed, parseFloat, and Number() on price strings are banned. There’s exactly one place in the entire codebase where toFixed is allowed — building the UPI deep-link, because the UPI specification literally requires decimal rupees in the URL.

CODE · lib/upi.ts 
export function buildUpiDeepLink({ upiId, name, amountRupees, billRef }: BuildUpiDeepLinkParams): string {
  const am = amountRupees.toFixed(2);
  const params = new URLSearchParams({
    pa: upiId,
    pn: name,
    am,
    cu: "INR",
    tn: billRef,
  });
  return `upi://pay?${params.toString()}`;
}
PLAIN ENGLISH

Build the URL that the customer’s phone interprets as “open my UPI app, fill in this payment.”

The UPI spec says the am parameter must be in decimal rupees with two decimal places — e.g., 40.00, not 4000. So we use toFixed(2) here, and only here.

Pack the parameters into a URL: pa = payee address (vendor’s UPI ID), pn = payee name, am = amount, cu = currency, tn = transaction note (the bill number).

Return upi://pay?.... The browser turns this into a QR code; the customer scans it with GPay / PhonePe / Paytm.

📜
A grep that runs on every build

To stop new toFixeds from sneaking in, the project recommends a CI check: rg -l "toFixed" --glob '!lib/upi.ts' --glob '!*.md' app/ components/ lib/ workers/. If that command finds anything, the build fails — the only allowed exception is the file above.

Server-side recompute

The browser sends the cart and totals to the server. But the server doesn’t trust them — it recomputes them and rejects the request if they don’t match. This is one extra check that prevents an entire category of bugs.

CODE · app/api/transactions/route.ts 
const body = parsed.data;
const totals = checkTransactionTotals(body);
if (!totals.ok) {
  return NextResponse.json({ error: totals.code, code: totals.code }, { status: 400 });
}

const cap = PLAN_LIMITS[vendor.plan].monthlyTxnCap;
if (cap !== null) {
  const monthStart = getIstMonthStart();
  const count = await prisma.transaction.count({
    where: { vendorId: vendor.id, createdAt: { gte: monthStart } },
  });
  if (count >= cap) {
    throw new AuthError(402, "monthly_txn_cap_reached");
  }
}
PLAIN ENGLISH

Body has been validated by Zod (shape is right). Now check the math.

checkTransactionTotals recomputes subtotal + tax - discount on the server and compares with what the browser sent.

If they don’t match, return 400 — either the cart is corrupted or someone tampered with it. Either way, refuse to charge.

Look up this vendor’s plan-cap (e.g., FREE = 50 transactions/month).

Count this month’s transactions, in IST.

If they’re at the cap, refuse with HTTP 402. The frontend catches it and shows an upgrade prompt.

After the sale

The customer walked away. The vendor is already taking the next order. But the WhatsApp receipt hasn’t sent yet. Razorpay’s server is about to POST a webhook with no logged-in user. Network calls will fail and retry. This module is about the part of the system that has to keep working even when nobody’s looking.

A postal sorting facility

Picture a postal sorting depot at 2 AM. Letters keep arriving on conveyor belts. Some get delivered immediately, some need a second sorting pass, some get returned to sender. The depot isn’t magic — it’s built around three boring rules:

📬

Durable mailbag

Once a letter goes in the mailbag (the queue), it can’t fall out. Even if the depot building catches fire, the bag’s contents survive on disk.

🔁

Retries with patience

Recipient’s door is locked? Try again in 5 seconds, then 10, then 20. Never just give up. Never just try again instantly forever.

🪪

Tracking ID per letter

Same letter showing up twice? Check the tracking ID. If we already delivered it, just discard the second copy. Don’t bother the recipient.

In AwaazOS, the mailbag is BullMQ. The post office is the Fly.io worker. The tracking ID is the whatsappSent flag. Let’s zoom in.

The idempotency check, in seven lines

The single most important part of the worker is also the smallest. If a job runs twice (because of a retry, a network blip, or anything else), the customer should get exactly one WhatsApp message — not two.

CODE · workers/receipt.worker.ts 
const tx = await prisma.transaction.findFirst({
  where: { id: transactionId, vendorId },
  include: { orderItems: { /* ... */ }, receipt: true, vendor: { include: { settings: true } } },
});

if (!tx || !tx.receipt) {
  logger.warn({ transactionId, vendorId }, "transaction or receipt not found; dropping job");
  return;
}

if (tx.receipt.whatsappSent) {
  logger.info({ transactionId }, "receipt already sent; idempotent skip");
  return;
}
PLAIN ENGLISH

Look up the transaction by transactionId AND vendorId. (The same compound-where pattern as Module 3 — even the worker can’t cross tenants.)

Pull in everything we need to format the message: line items, the receipt row, vendor name & settings.

If the row doesn’t exist (deleted? wrong ID?), just drop the job. We can’t send a message about a sale that doesn’t exist.

The idempotency check. If whatsappSent is already true, somebody already delivered this. Quietly return without sending again.

Log it for visibility, but treat it as a normal outcome — no retries, no errors. The job is “done.”

🔁
Engineers call this “at-least-once with idempotency”

Distributed systems can’t guarantee a job runs exactly once — networks fail, machines crash, ack’s get lost. So the next-best thing is: guarantee jobs run at least once, and design every worker so re-runs are safe. The whatsappSent flag is the “safe to re-run” design here.

The webhook with no login

Razorpay needs to tell us when a vendor pays for their subscription. They POST to /api/webhooks/razorpay — but their server doesn’t have a vendor session. Anyone on the internet could try to POST the same URL. So how do we know it’s really Razorpay?

By checking a HMAC signature. Razorpay signs the request body with a shared secret. We re-compute the signature on our end and compare. Only the real Razorpay can produce a matching signature.

CODE · app/api/webhooks/razorpay/route.ts 
const rawBody = await req.text();
const sig = req.headers.get("x-razorpay-signature");
if (!verifyRazorpaySignature(rawBody, sig)) {
  return NextResponse.json({}, { status: 401 });
}

let body: unknown;
try {
  body = JSON.parse(rawBody) as unknown;
} catch {
  console.warn("[webhooks/razorpay] invalid json");
  return NextResponse.json({ ok: true });
}
PLAIN ENGLISH

Read the request body as raw text. Critical: do not parse to JSON yet. Different JSON libraries reorder keys, which would break signature verification.

Read the header where Razorpay puts the signature.

Verify: re-compute HMAC-SHA256 of the raw body using our shared secret, and compare against the header. Comparison uses crypto.timingSafeEqual to defeat timing attacks.

If the signature doesn’t match, return 401 with an empty body — don’t even confirm the URL exists.

Only NOW it’s safe to JSON.parse the body, since we’ve verified the sender.

If the JSON is malformed (which shouldn’t happen post-signature-check), shrug and return 200 OK so Razorpay doesn’t spam-retry.

🔐
Verify before you read

The single most common webhook bug: trusting the body before checking the signature. The signature check goes first, before any database lookup, before any JSON parse, before any business logic. If the signature is wrong, you bounce without doing any work that could be exploited.

Plan gates — HTTP 402 in disguise

Some features are paid-only — WhatsApp receipts (STARTER+), CSV exports (PRO+), unlimited transactions (PRO+). Rather than scattering if (vendor.plan === "FREE") return ... through the code, AwaazOS uses a single helper that throws a structured error.

CODE · lib/rbac.ts 
export class PlanGateError extends AuthError {
  constructor(
    public readonly required: Plan,
    public readonly current: Plan,
  ) {
    super(402, "Plan upgrade required");
    this.name = "PlanGateError";
  }
}

export function requirePlan(vendor: { plan: Plan }, minPlan: Plan): void {
  if (PLAN_RANK[vendor.plan] < PLAN_RANK[minPlan]) {
    throw new PlanGateError(minPlan, vendor.plan);
  }
}
PLAIN ENGLISH

Define a special error class that carries both the required plan and the current plan.

It uses HTTP 402 (“Payment Required”) as its status code. The frontend listens for 402s and shows an upgrade button automatically.

A one-line guard: requirePlan(vendor, "STARTER"). If the vendor’s plan is too low, throw the error — the route handler’s try/catch translates it into a structured 402 response.

The error carries enough context for the upgrade prompt to say “you’re on FREE, this needs STARTER” rather than a generic “please upgrade.”

💳
Plan capabilities at a glance

FREE: 50 transactions/month, no WhatsApp, 7 days of analytics.
STARTER: 500 transactions/month, WhatsApp on, 90 days of analytics.
PRO: unlimited transactions, CSV export, 365 days of analytics.
One table in lib/constants.ts; the whole app reads from it.
