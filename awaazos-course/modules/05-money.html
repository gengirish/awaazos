Money in paise — the atomic transaction

When the vendor taps Mark as Paid, five things must happen to the database. They have to either all succeed together or all fail together — never four out of five. This module is about the two disciplines that make that possible: integer paise math, and a five-step database transaction.

Synchronised swimmers

Picture a synchronised swimming team. On the count of three, all five swimmers dive together. They’re trained for one rule: if even one swimmer hesitates, none of them dive. They re-set, count again, dive together. The judges either see five splashes or zero. Never four.

Database transactions work exactly like this. AwaazOS’s “Mark as Paid” bundles five separate writes into one transaction:

1
Get the next bill number

Atomically increment today’s counter for this vendor. Becomes AWZ-20260430-0001.

2
Insert the Transaction row

Subtotal, tax, total, payment method, payment status — all in paise.

3
Insert each OrderItem

One row per line in the cart, with the price snapshotted at sale time.

4
Bump the DailySummary

Add this sale to today’s rollup so the analytics dashboard updates immediately.

5
Create the Receipt row

Marker that this transaction’s receipt has not yet been sent on WhatsApp.

If any one of these fails, all five roll back — the database returns to exactly the state it was in before the swimmer climbed onto the platform. No half-recorded sales. No bill numbers wasted. Ever.

Why paise, not rupees

Before we touch the transaction, we have to talk about the unit of money. AwaazOS stores every monetary amount as an integer number of paise. ₹20 is the integer 2000. ₹99.50 is 9950. Never decimals.

💸
Why floats are forbidden for money

Computers store decimal numbers like 0.1 and 0.2 approximately. Try this in any browser console: 0.1 + 0.2 === 0.3 evaluates to false. Add a tiny rounding error to a million sales and you’re off by hundreds of rupees, with no way to find which sale caused it. Integer paise dodges the entire problem.

CODE · lib/currency.ts 
export function rupeesToPaise(rupees: number): number {
  if (!Number.isFinite(rupees)) {
    throw new Error("Invalid rupee amount");
  }
  const scaled = rupees * 100;
  const rounded = Math.round(scaled);
  if (Math.abs(scaled - rounded) > 1e-9) {
    throw new Error("Rupee amount must have at most 2 decimal places");
  }
  return rounded;
}

export function formatINR(paise: number): string {
  if (!Number.isInteger(paise)) {
    throw new Error("paise must be an integer");
  }
  const rupees = paiseToRupees(paise);
  return new Intl.NumberFormat("en-IN", {
    style: "currency",
    currency: "INR",
    minimumFractionDigits: 2,
    maximumFractionDigits: 2,
  }).format(rupees);
}
PLAIN ENGLISH

Convert rupees (a friendly number like 20.5) into paise (the integer 2050).

Reject anything that isn’t a finite number — NaN, Infinity, etc.

Multiply by 100 to scale into paise.

Round to the nearest integer (in case the multiplication produced a tiny float artefact).

If the difference between the multiplication result and the rounded integer is bigger than a tiny epsilon, the user passed something like ₹20.005 — reject it explicitly rather than silently rounding.

Format paise back into a display string. Used everywhere on the screen.

Use the browser’s built-in en-IN formatter so we get correct Indian grouping (₹1,23,456 with the lakh comma in the right place) for free.

The five swimmers, in code

Here’s the heart of POST /api/transactions — the five writes wrapped in a single prisma.$transaction call.

CODE · app/api/transactions/route.ts 
const { transaction, receipt } = await prisma.$transaction(async (tx) => {
  const seq = await tx.billSequence.upsert({
    where: { vendorId_date: { vendorId: vendor.id, date: today } },
    create: { vendorId: vendor.id, date: today, lastSeq: 1 },
    update: { lastSeq: { increment: 1 } },
  });

  const ymd = formatBillDateYYYYMMDD(today);
  const billNumber = `AWZ-${ymd}-${String(seq.lastSeq).padStart(4, "0")}`;

  const transactionRow = await tx.transaction.create({
    data: {
      vendorId: vendor.id, billNumber,
      subtotalPaise: body.subtotalPaise, taxPaise: body.taxPaise, totalPaise: body.totalPaise,
      orderItems: { create: body.items.map((i) => ({
        menuItemId: i.menuItemId, name: i.name,
        priceInPaise: i.priceInPaise, qty: i.qty,
        totalPaise: i.priceInPaise * i.qty,
      })) },
    },
  });

  await tx.dailySummary.upsert({ /* increment all aggregates */ });

  const receiptRow = await tx.receipt.create({
    data: { transactionId: transactionRow.id, vendorId: vendor.id, receiptNumber: billNumber, whatsappSent: false },
  });

  return { transaction: transactionRow, receipt: receiptRow };
});
PLAIN ENGLISH

Open a database transaction. Everything inside the curly braces will commit together — or roll back together if anything throws.

Step 1 — Upsert the bill counter for (this vendor, today). If it doesn’t exist, create it at 1. If it does, add 1 atomically.

Format today’s date in IST as YYYYMMDD. Build the bill number string — e.g., AWZ-20260430-0001.

Step 2 — insert the Transaction row with all the paise totals.

Step 3 — nested inside, insert one OrderItem per cart line. Note name and priceInPaise are copied here, not joined — the bill is a snapshot, not a live link to the menu.

Step 4 — bump today’s rollup row so analytics see the sale immediately.

Step 5 — create the Receipt row, with a flag saying WhatsApp hasn’t been sent yet (a worker will flip that later).

If we got here, all five swimmers dove together. The transaction commits. We return the rows for the response.

Engineers call this property “atomicity”

It’s the “A” in ACID. The whole reason real businesses store money in databases like Postgres rather than in spreadsheets or in-memory caches: the transaction either commits in full or doesn’t happen at all. Cosmic rays could flip a bit, the server could die mid-write — either way, the database never ends up in a half-state.

The one allowed toFixed

The rule of the codebase: toFixed, parseFloat, and Number() on price strings are banned. There’s exactly one place in the entire codebase where toFixed is allowed — building the UPI deep-link, because the UPI specification literally requires decimal rupees in the URL.

CODE · lib/upi.ts 
export function buildUpiDeepLink({ upiId, name, amountRupees, billRef }: BuildUpiDeepLinkParams): string {
  const am = amountRupees.toFixed(2);
  const params = new URLSearchParams({
    pa: upiId,
    pn: name,
    am,
    cu: "INR",
    tn: billRef,
  });
  return `upi://pay?${params.toString()}`;
}
PLAIN ENGLISH

Build the URL that the customer’s phone interprets as “open my UPI app, fill in this payment.”

The UPI spec says the am parameter must be in decimal rupees with two decimal places — e.g., 40.00, not 4000. So we use toFixed(2) here, and only here.

Pack the parameters into a URL: pa = payee address (vendor’s UPI ID), pn = payee name, am = amount, cu = currency, tn = transaction note (the bill number).

Return upi://pay?.... The browser turns this into a QR code; the customer scans it with GPay / PhonePe / Paytm.

📜
A grep that runs on every build

To stop new toFixeds from sneaking in, the project recommends a CI check: rg -l "toFixed" --glob '!lib/upi.ts' --glob '!*.md' app/ components/ lib/ workers/. If that command finds anything, the build fails — the only allowed exception is the file above.

Server-side recompute

The browser sends the cart and totals to the server. But the server doesn’t trust them — it recomputes them and rejects the request if they don’t match. This is one extra check that prevents an entire category of bugs.

CODE · app/api/transactions/route.ts 
const body = parsed.data;
const totals = checkTransactionTotals(body);
if (!totals.ok) {
  return NextResponse.json({ error: totals.code, code: totals.code }, { status: 400 });
}

const cap = PLAN_LIMITS[vendor.plan].monthlyTxnCap;
if (cap !== null) {
  const monthStart = getIstMonthStart();
  const count = await prisma.transaction.count({
    where: { vendorId: vendor.id, createdAt: { gte: monthStart } },
  });
  if (count >= cap) {
    throw new AuthError(402, "monthly_txn_cap_reached");
  }
}
PLAIN ENGLISH

Body has been validated by Zod (shape is right). Now check the math.

checkTransactionTotals recomputes subtotal + tax - discount on the server and compares with what the browser sent.

If they don’t match, return 400 — either the cart is corrupted or someone tampered with it. Either way, refuse to charge.

Look up this vendor’s plan-cap (e.g., FREE = 50 transactions/month).

Count this month’s transactions, in IST.

If they’re at the cap, refuse with HTTP 402. The frontend catches it and shows an upgrade prompt.
