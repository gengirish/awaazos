The Cast: three providers, one alias

When you visit awaazos.vercel.app, it feels like one app. Behind the curtain, three different cloud companies and four external APIs are doing different jobs. Here’s who does what — and, just as importantly, why none of them does everything.

The right tool for the job

Picture a wood-working workshop. You have a circular saw for straight cuts, a router for edge profiles, a drill press for clean perpendicular holes. You wouldn’t ask the circular saw to also drill holes — the result would be terrible at both jobs. You pick the specialist tool for each task.

AwaazOS is the same. Each provider in the stack is the best in the world at one specific thing. Putting everything on one provider would be slower, more expensive, or less reliable.

🛠️
Engineers call this “separation of concerns”

One component, one job. The benefit isn’t academic — it’s that when something breaks, you know exactly which specialist to call.

Why the workers live somewhere else

This is the most-asked question about the architecture. Here’s the simple version: a Vercel serverless function is fast for short jobs, but it’s a terrible fit for the kind of work that needs to wait around — like watching a queue for new WhatsApp jobs.

⚡

Serverless (Vercel)

Wakes up, runs for <10 seconds, sleeps. Perfect for “take this voice clip and parse it.” Bad at “wait around forever for jobs.”

⚙️

Long-running (Fly.io)

A small Linux box that’s always on. Holds a TCP connection to Redis. Picks up jobs the second they appear. Perfect for queue workers.

🗄️

Database (Neon)

Stores everything. Both Vercel and Fly read/write to the same Neon database — that’s how the two halves of the system stay in sync.

💡
The two-Redis trick

You’ll see two Redis instances in the diagram. They’re different on purpose. Upstash REST talks over HTTP and is used by Vercel for rate-limiting. Regular TCP Redis is used by BullMQ on Fly because BullMQ needs to keep a connection open. You can’t use the wrong one in the wrong place.

The middleware in five lines

Every single request that hits AwaazOS — whether it’s a vendor visiting /menu or an API call to /api/transactions — passes through this tiny file first. It runs on Vercel’s edge in roughly 10 milliseconds.

CODE · middleware.ts 
import NextAuth from "next-auth";
import { authConfig } from "@/lib/auth.config";

export const { auth: middleware } = NextAuth(authConfig);

export const config = {
  matcher: [
    "/((?!_next/static|_next/image|favicon.ico|api/webhooks|api/health|api/ready).*)",
  ],
};
PLAIN ENGLISH

Bring in the Auth.js library and our shared auth settings.

Hand off the request to Auth.js. It checks the cookie for a valid session.

Tell Vercel which URLs this middleware should run on.

The matcher is a regex that says: “run on every URL except static files, webhook callbacks (those verify themselves), and health-check probes (uptime monitors must reach them anonymously).”

⚠️
Don’t accidentally protect a webhook

If /api/webhooks/razorpay were behind auth, Razorpay’s servers (which don’t have a vendor login) couldn’t reach it — and subscriptions would silently break. Excluding webhooks from the matcher is a small line with big consequences.

Quick check

Less about memorising the cast list, more about the reasoning. If you can answer these, you can debug a lot of production issues.

Why can’t the WhatsApp-receipt worker just run on Vercel like the rest of the API?

Razorpay needs to POST to /api/webhooks/razorpay when a subscription gets paid. There’s no vendor logged in for those calls. How does the system handle that securely?

A new engineer asks: “Why don’t we just put everything on one provider to simplify operations?” What’s the strongest counter-argument from this codebase?

A useful mental shortcut

🧭
Where would I look for ___?

When something breaks, the first question is always which provider owns this?
UI bugs & slow page loads → Vercel logs.
WhatsApp didn’t arrive → Fly worker logs.
Sale didn’t save → Neon query logs.
AI parse was wrong → VoiceParseLog table in Neon.
Subscription stuck → Razorpay dashboard + webhook logs.
Knowing this saves an hour every time something goes wrong.
