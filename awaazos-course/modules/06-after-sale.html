After the sale

The customer walked away. The vendor is already taking the next order. But the WhatsApp receipt hasn’t sent yet. Razorpay’s server is about to POST a webhook with no logged-in user. Network calls will fail and retry. This module is about the part of the system that has to keep working even when nobody’s looking.

A postal sorting facility

Picture a postal sorting depot at 2 AM. Letters keep arriving on conveyor belts. Some get delivered immediately, some need a second sorting pass, some get returned to sender. The depot isn’t magic — it’s built around three boring rules:

📬

Durable mailbag

Once a letter goes in the mailbag (the queue), it can’t fall out. Even if the depot building catches fire, the bag’s contents survive on disk.

🔁

Retries with patience

Recipient’s door is locked? Try again in 5 seconds, then 10, then 20. Never just give up. Never just try again instantly forever.

🪪

Tracking ID per letter

Same letter showing up twice? Check the tracking ID. If we already delivered it, just discard the second copy. Don’t bother the recipient.

In AwaazOS, the mailbag is BullMQ. The post office is the Fly.io worker. The tracking ID is the whatsappSent flag. Let’s zoom in.

The idempotency check, in seven lines

The single most important part of the worker is also the smallest. If a job runs twice (because of a retry, a network blip, or anything else), the customer should get exactly one WhatsApp message — not two.

CODE · workers/receipt.worker.ts 
const tx = await prisma.transaction.findFirst({
  where: { id: transactionId, vendorId },
  include: { orderItems: { /* ... */ }, receipt: true, vendor: { include: { settings: true } } },
});

if (!tx || !tx.receipt) {
  logger.warn({ transactionId, vendorId }, "transaction or receipt not found; dropping job");
  return;
}

if (tx.receipt.whatsappSent) {
  logger.info({ transactionId }, "receipt already sent; idempotent skip");
  return;
}
PLAIN ENGLISH

Look up the transaction by transactionId AND vendorId. (The same compound-where pattern as Module 3 — even the worker can’t cross tenants.)

Pull in everything we need to format the message: line items, the receipt row, vendor name & settings.

If the row doesn’t exist (deleted? wrong ID?), just drop the job. We can’t send a message about a sale that doesn’t exist.

The idempotency check. If whatsappSent is already true, somebody already delivered this. Quietly return without sending again.

Log it for visibility, but treat it as a normal outcome — no retries, no errors. The job is “done.”

🔁
Engineers call this “at-least-once with idempotency”

Distributed systems can’t guarantee a job runs exactly once — networks fail, machines crash, ack’s get lost. So the next-best thing is: guarantee jobs run at least once, and design every worker so re-runs are safe. The whatsappSent flag is the “safe to re-run” design here.

The webhook with no login

Razorpay needs to tell us when a vendor pays for their subscription. They POST to /api/webhooks/razorpay — but their server doesn’t have a vendor session. Anyone on the internet could try to POST the same URL. So how do we know it’s really Razorpay?

By checking a HMAC signature. Razorpay signs the request body with a shared secret. We re-compute the signature on our end and compare. Only the real Razorpay can produce a matching signature.

CODE · app/api/webhooks/razorpay/route.ts 
const rawBody = await req.text();
const sig = req.headers.get("x-razorpay-signature");
if (!verifyRazorpaySignature(rawBody, sig)) {
  return NextResponse.json({}, { status: 401 });
}

let body: unknown;
try {
  body = JSON.parse(rawBody) as unknown;
} catch {
  console.warn("[webhooks/razorpay] invalid json");
  return NextResponse.json({ ok: true });
}
PLAIN ENGLISH

Read the request body as raw text. Critical: do not parse to JSON yet. Different JSON libraries reorder keys, which would break signature verification.

Read the header where Razorpay puts the signature.

Verify: re-compute HMAC-SHA256 of the raw body using our shared secret, and compare against the header. Comparison uses crypto.timingSafeEqual to defeat timing attacks.

If the signature doesn’t match, return 401 with an empty body — don’t even confirm the URL exists.

Only NOW it’s safe to JSON.parse the body, since we’ve verified the sender.

If the JSON is malformed (which shouldn’t happen post-signature-check), shrug and return 200 OK so Razorpay doesn’t spam-retry.

🔐
Verify before you read

The single most common webhook bug: trusting the body before checking the signature. The signature check goes first, before any database lookup, before any JSON parse, before any business logic. If the signature is wrong, you bounce without doing any work that could be exploited.

Plan gates — HTTP 402 in disguise

Some features are paid-only — WhatsApp receipts (STARTER+), CSV exports (PRO+), unlimited transactions (PRO+). Rather than scattering if (vendor.plan === "FREE") return ... through the code, AwaazOS uses a single helper that throws a structured error.

CODE · lib/rbac.ts 
export class PlanGateError extends AuthError {
  constructor(
    public readonly required: Plan,
    public readonly current: Plan,
  ) {
    super(402, "Plan upgrade required");
    this.name = "PlanGateError";
  }
}

export function requirePlan(vendor: { plan: Plan }, minPlan: Plan): void {
  if (PLAN_RANK[vendor.plan] < PLAN_RANK[minPlan]) {
    throw new PlanGateError(minPlan, vendor.plan);
  }
}
PLAIN ENGLISH

Define a special error class that carries both the required plan and the current plan.

It uses HTTP 402 (“Payment Required”) as its status code. The frontend listens for 402s and shows an upgrade button automatically.

A one-line guard: requirePlan(vendor, "STARTER"). If the vendor’s plan is too low, throw the error — the route handler’s try/catch translates it into a structured 402 response.

The error carries enough context for the upgrade prompt to say “you’re on FREE, this needs STARTER” rather than a generic “please upgrade.”

💳
Plan capabilities at a glance

FREE: 50 transactions/month, no WhatsApp, 7 days of analytics.
STARTER: 500 transactions/month, WhatsApp on, 90 days of analytics.
PRO: unlimited transactions, CSV export, 365 days of analytics.
One table in lib/constants.ts; the whole app reads from it.
